## 1. Synchronous generation path

### 1.1 V1 trainer (DEFAULT: `trainer.use_v1: true`, `ppo_trainer.yaml:232`; `trainer_mode: sync`, `:238`)

Modules: `verl/trainer/ppo/v1/{trainer_base.py (2028 l), trainer_sync.py, trainer_colocate_async.py, trainer_separate_async.py (453 l), agent_loop_tq.py (262 l), replay_buffer.py (613 l)}`. Selected in `main_ppo.py:187-195` (`TaskRunnerV1`); V0 prints a deprecation warning.

**Per step, sync mode** (`trainer_base.py:534-613`, `trainer_sync.py:24-44`):

1. `prepare_step` → `_add_batch_to_generate` (`trainer_base.py:1521-1528`): fetch `train_batch_size` prompts (`:1480-1495`, one `uuid` per prompt `:1477`), register them in TransferQueue as `{"is_prompt": True, "status": "pending"}` (`:1497-1510`) and **fire-and-forget** `AgentLoopManagerTQ.generate_sequences` (`agent_loop_tq.py:248-262`): static `prompts.chunk(num_workers)` by **prompt**, `ray.get` only on the dispatch RPC.
2. `AgentLoopWorkerTQ.generate_sequences` (`agent_loop_tq.py:61-110`) creates one background task per prompt; `_run_prompt` (`:112-153`) marks the prompt `running` in TQ and spawns **n sibling agent loops** (`session_id=i`, `:127-134`) — so **dispatch is per prompt and the n GRPO siblings live on the same AgentLoopWorker**, but each sibling still gets its own `uuid4` `request_id` (`single_turn_agent_loop.py:69`) and is routed independently by the least-inflight balancer (§5). Each finished trajectory is `kv_batch_put` into TQ **unpadded** (`:187-232`) with tags `{status, prompt_len, response_len, seq_len, global_steps, min/max_global_steps}`; the prompt flips to `finished`/`failure` after all n settle (`:136-148`).
3. `_step_once` (`trainer_base.py:563-613`): the `gen` timer wraps `ReplayBuffer.sample(global_steps, "train", sample_batch_size)` (`:566-575`). `sample` (`replay_buffer.py:422-511`) loops: `tq.kv_list()` of the **entire partition** (`:210`, rebuilt into Python dicts every poll `:201-235`) → evict → `has_enough_samples = len(sampleable) >= batch_size` (`:462`) → else `time.sleep(poll_interval=2.0)` (`:144`, `:408-409`). A batch is ready only when **all** requested prompt groups are terminal, i.e. the step still waits for the slowest trajectory of the slowest group; the 2 s poll adds up to 2 s (mean ≈ 1 s) of dead time per sample call, and sync selects oldest-first by prompt `global_steps` (`:383-392`).
4. `on_sample_end` → `sleep_replicas` (`trainer_sync.py:40-42`); `on_step_end` → `update_weights` (`:35-38`). Rollout does not overlap training in sync mode (same as V0).
5. Opt-in **DAPO group filtering = the only over-sampling that exists** (`replay_buffer.py:442-501`): with `filter_groups_metric` set, evicting k zero-variance groups grants `2k` refill credit (`:475`), bounded by `max_inflight_gen_batches × train_batch_size` in flight (`:447`, `:478`); once enough groups are sampleable the buffer **drains** the in-flight requests (`can_select` requires `inflight_count == 0`, `:488`) and discards the surplus (`:494-500`). So extra prompts are never aborted — they are waited for, then thrown away: the opposite of straggler control.
6. `colocate_async` (`trainer_colocate_async.py`) differs only in: `FullyAsyncLLMServerClient` (`:26-28`), warm-up batches (`:34-35`), `abort_replicas()` before sleep (`:44-48`) and `resume_generation_replicas()` after the weight update (`:37-42`); `ReplayBufferAsync` evicts/refills stale groups (`replay_buffer.py:514-613`, threshold 8 versions, strategy `drop`, `ppo_trainer.yaml:298-303`).

**What changed vs V0 and what did not.** V1 removes the padded gather (trajectories are stored at true length, the trainer pulls `KVBatchMeta` keys), dispatches by prompt, and gives async modes partial rollout + staleness control. It keeps: static chunking across 8 workers, independent routing of the n siblings, a global single-actor load balancer, one `uuid`-per-turn vLLM request id, full `reset_prefix_cache` on every wake/update, and a polling replay buffer (2 s) that only becomes ready when the last group finishes.

**Roadmap P1 "sample-level dispatch: dispatch next prompt once #completed samples >= group size"** (#8186, unclaimed): nothing of it exists. The hooks are all there — `refill_fn=self._add_prompts_to_generate` (`trainer_base.py:162`, exact-count dispatch `:1515-1518`), per-group terminal status in TQ, `ReplayBufferAsync.get_sampleable_count` (`replay_buffer.py:558-562`). Smallest valuable PR: in `ReplayBuffer.sample` (sync) and `wait_for_sampleable` (async), maintain a `target_inflight` and call `refill_fn(k)` whenever `finished_groups_since_last_refill >= k` so the engines never drain below `max_num_seqs × replicas` while the trainer waits — combined with a sync-mode "abort the stragglers once `batch_size` groups are sampleable" (the config knob `over_sample_rate` already exists with **no consumer anywhere in the clone**: `grep -rn over_sample_rate verl recipe examples` hits only `workers/config/rollout.py:214-215` and the generated yamls). Poll latency: replace `time.sleep(2.0)` with a TQ notification or a 0.1-0.2 s poll (the per-poll cost is a `kv_list` of ≤ B×n+B entries, ≈ 5k dict updates — sub-millisecond).

### 1.2 V0 path (`verl/trainer/ppo/ray_trainer.py`) — still what most recipes exercise

Per step:

1. `gen_batch.repeat(repeat_times=rollout_n, interleave=True)` (`ray_trainer.py:1491`): the n GRPO samples of a prompt become n adjacent rows of one `DataProto`; nothing downstream knows they share a prefix except the `index`/`uid` column.
2. `self.async_rollout_manager.generate_sequences(combined_gen_batch)` then `self.checkpoint_manager.sleep_replicas()` (`ray_trainer.py:1513-1514`). The whole step is `gen` → sleep → reward/old_logprob/update → `update_weights` (`:1715-1716`, which wakes the engine).
3. `AgentLoopManager.generate_sequences` (`agent_loop.py:1250-1272`): assigns a per-row `priority = arange` (`:1259`, only honoured if `scheduling_policy=priority`), **statically chunks** the batch into `len(agent_loop_workers)` = 8 equal slices (`:1264`), fires one Ray RPC per worker and `asyncio.gather`s all 8 (`:1265-1270`). The gather returns only when the *last sequence of the whole batch* finishes; the code's own comment says so (`:1301` "batch sequence generation is bounded by the slowest sample") and the only mitigation is a metric (`agent_loop/slowest/*`).
4. `AgentLoopWorker.generate_sequences` (`agent_loop.py:600-690`): one `asyncio.Task` per row (`:674-685`), each `hydra.utils.instantiate`s a fresh `AgentLoopBase` object (`:712-722`) → `create_continuous_token_builder` runs per trajectory (`agent_loop.py:282-288`): cheap but it is 4096 object builds/step.
5. `SingleTurnAgentLoop.run` (`single_turn_agent_loop.py:38-115`): `apply_chat_template` once per row in the default executor (`:54`, `agent_loop.py:366-376`) — so the identical prompt is rendered **n times**; `request_id = uuid4().hex` per row (`:69`) → the n siblings are routed independently (§5).
6. `LLMServerClient.generate` (`llm_server.py:95-162`): **two Ray RPC hops per LLM call** — `_acquire_server` to the single `GlobalRequestLoadBalancer` actor (`:69-80`, `router.py:170-204`) and `server.generate.remote` to the replica actor (`:140-151`); release is fire-and-forget (`:82-87`). A fresh vLLM request id per turn (`:89-93`); `session_id=request_id` pins the DP engine (`vllm_async_server.py:845-850`).
7. `vLLMHttpServer.generate` (`vllm_async_server.py:590-837`): builds `SamplingParams` per request, `detokenize=False` (`:679-680`), parks behind the submission gate (`:715-717`, `:1231-1253`), `engine.add_request` + per-request queue drain (`:1255-1317`), then extracts logprobs (`:757-791`).
8. Postprocess per row (`agent_loop.py:755-871`): `tokenizer.pad` to `prompt_length` (left) and `response_length` (right) → every row is materialised at full width `[1, P+R]` for `prompts/responses/response_mask/input_ids/attention_mask/position_ids` (+ fp32 `rollout_log_probs`), then `torch.cat` across the chunk (`:1083-1089`) and `DataProto.concat` on the driver (`:1268`).
9. Sleep: `vLLMReplica.sleep` waits for drain then `engine.sleep(level=2)` for full-weight hybrid (`vllm_async_server.py:1511-1527`, `:1546-1556`); wake is `engine.wake_up(["kv_cache","weights"])` + `reset_prefix_cache` (`:924-933`). CUDA graphs are *not* re-captured (vLLM sleep mode keeps them; cf. rollout.yaml:57-59); KV is re-mapped by CuMemAllocator; level-2 discards the weight *bytes*, so every wake needs a full reload (§3).

**Where the time goes (est., reference workload).**

- *Long tail*: 4096 sequences over 1024 decode slots is ≥4 waves. Decode step latency is roughly constant (weight-bandwidth bound) while the number of live sequences drains from 1024 to 1, so the last wave's tail produces few tokens per step. The project's own colocate numbers (`docs/advance/fully_async.md`, Qwen2.5-Math-7B, 28k cap, 32 H20) put `gen` at 357 s of a 790 s step (45 %); the one-step-off doc states DAPO-32B rollout ≈ 70 % of step time and "increasing resources does not reduce the Rollout duration" (`docs/advance/one_step_off.md` background). Nothing in the V0 path shortens the tail: no over-sampling, no partial rollout, no abort-at-threshold.
- *`over_sample_rate`*: declared in `rollout.yaml:137-139` with an "abort remaining requests when (1-rate)·total complete" contract, but `grep -rn over_sample_rate verl/` finds no consumer outside the config dataclass (verified below in §6 table) — a documented knob with no implementation in the clone.
- *Gather/pad path*: per row `(2×1.5k + 4×8k... )` → with P=2048, R=8192: `prompts` 2048 + `responses` 8192 + `response_mask` 8192 + `input_ids` 10240 + `attention_mask` 10240 + `position_ids` 10240 = 49 152 int64 = 393 KB + `rollout_log_probs` 32 KB ≈ **425 KB/row → 1.7 GB/step** crossing Ray object store from 8 workers to the driver, plus a second copy in `DataProto.concat`. At ~1-2 GB/s pickling this is **1-3 s/step (est.)**, all on the driver's critical path, and int64 for masks/ids is 4-8× larger than needed.
- *Control-plane RPC*: 4096 `acquire_server` calls hit one Ray actor at step start; a single-threaded actor sustains ~1-3k trivial calls/s **(guess)** → the last request is *admitted* ~1.5-4 s after the first; multi-turn multiplies this by turns. The replica actor side is fine (`max_concurrency=1024`).
- *Per-row Python*: 4096 × (hydra instantiate + token-author construction + `apply_chat_template` ≈ 1-3 ms) ≈ 4-12 CPU-s/step, spread over 8 workers → **0.5-1.5 s wall (est.)**, GIL-bound per worker.

### 1.3 Agent-loop worker placement

`AgentLoopManager._init_agent_loop_workers` round-robins the 8 workers over all alive CPU nodes (`agent_loop.py:1232-1248`, soft node affinity). Reward computation is streamed per trajectory to a random `RewardLoopWorker` (`agent_loop.py:1052-1055`) when no colocated RM is used (`ray_trainer.py:947-948`).

### 1.4 Straggler handling that exists today

- Partial rollout (abort + resume with retained tokens) exists only via `FullyAsyncLLMServerClient` (`llm_server.py:165-380`): on `stop_reason in ("aborted","abort")` it re-issues `prompt_ids + tokens_so_far` with a shrunk `max_tokens` (`:294-300`, `:351-355`) after a 1 s sleep (`:366`). The resumed request **re-prefills the retained prefix** (vLLM prefix cache was reset by the weight update, `vllm_rollout.py:247-248`), which is exactly roadmap P0 ("no re-prefill on resume").
- The vLLM submission gate (`vllm_async_server.py:1168-1207`, merged #8397) makes `abort_all_requests` safe while requests are queued in WAITING; `pause_generation(mode="abort")` on vLLM ≥0.32 (`:1198-1199`).
- V0 `generate_sequences` never calls abort; the only V0 consumer of abort is `CheckpointEngineManager.update_weights` for non-naive backends (`base.py:522-523`).

## 3. Weight-sync transport (trainer → rollout)

### 3.1 DEFAULT: `naive` (colocated hybrid), FSDP → vLLM

Call chain per step: `ray_trainer.py:1716` → `CheckpointEngineManager.update_weights` → `backend == "naive"` → `actor_wg.update_weights(mode="naive")` (`checkpoint_engine/base.py:518-520`) → `EngineWorker.update_weights` (`engine_workers.py:785-886`):

1. `rollout.resume(tags=["weights"])` (`:840-841`) → `engine.wake_up(["weights"])`: allocate (uninitialised) weight buffers.
2. `get_per_tensor_param()` (`:845`) → FSDP: `self.module.state_dict()` then a generator doing `param.to(device).full_tensor()` **per parameter** (`engine/fsdp/transformer_impl.py:1020-1039`). The FSDP training dtype is forced to **fp32** (`transformer_impl.py:265-266`) and there is **no cast to the rollout dtype anywhere on the sender** (`bucketed_weight_transfer.py:118-125` explicitly declines to cast). So the wire carries **fp32: 32.8 GB for Qwen3-8B, 131 GB for a 32B**, and vLLM's `load_weights` does the fp32→bf16 cast on copy. Megatron exports via mbridge in model dtype (bf16) (`engine/megatron/transformer_impl.py:1004-1013`), so the 2× penalty is FSDP-specific.
3. `ServerAdapter.update_weights` (`vllm_rollout.py:210-253`): starts the receiver RPC (`update_weights_from_ipc`, `:229-233`) then `BucketedWeightSender.async_send_weights` (`bucketed_weight_transfer.py:102-166`): **one** 2 GiB device buffer (`:183`), tensors `copy_`'d into it (`:155-157`); when full: `synchronize()` → `send_pyobj(meta)` → **`recv()` blocks until the receiver has loaded the bucket** (`:134-136`). Receiver (`:269-309`): rebuilds the IPC view, calls `on_bucket_received` → `model.load_weights(bucket)` (`vllm_rollout/utils.py:326-330`, `:395-399`), `synchronize()`, then acks. **Zero overlap** between trainer all-gather/copy of bucket k+1 and engine load of bucket k; PR #5619 (draft, 2026-03) is the double-buffer proposal and is still open.
4. After the last bucket: `process_weights_after_loading` once (`utils.py:340-346`; MoE expert re-layout happens here), `clear_kv_cache` = `reset_prefix_cache` + mm/encoder caches (`vllm_rollout.py:247-248`, `vllm_async_server.py:962-971`), `set_global_steps`.
5. Trainer offloads params to CPU (`engine_workers.py:870-874`), `torch.distributed.barrier` (`:881`), `rollout.resume(["kv_cache"])` (`:882`).

**Bytes and copies per step, Qwen3-8B, 8 GPUs (each rank streams the *whole* model to its co-located vLLM worker):**

| stage | bytes/rank | copies |
|---|---|---|
| FSDP all-gather (fp32) | 32.8 GB produced, 28.7 GB received over NVLink | 1 (transient full tensor) |
| `copy_` into IPC bucket | 32.8 GB | 2 |
| vLLM `load_weights` copy + cast | 32.8 GB read, 16.4 GB write | 3 |
| buckets | 17 × 2 GiB (fp32) vs 9 if bf16 | 17 lock-step round trips |

Data-movement floor **(est.)**: ~0.3-0.6 s (NVLink + HBM). Observed colocated syncs are far above that (community reports 5-15 s for 7-8B, 20-40 s for 32B **(guess)**; the project's own disaggregated full-NCCL baselines are 5.5-6 s for Qwen2.5-7B and 34 s for Qwen3-8B FSDP2 2+2 nodes, `docs/advance/delta_weight_sync.md`), because the serialized per-bucket protocol adds ~450 per-tensor `full_tensor` collectives, 17 sync+ZMQ round trips, Python-level `load_weights` (≈450 tensor name resolutions + MoE mapping), `process_weights_after_loading`, `empty_cache`, and two `wake_up`s. For a 32B (131 GB fp32, 66 buckets) the same shape ≈ 4× worse.

**Smallest fixes (ordered by value/risk):**

- (a) **Cast to rollout dtype on the sender** when the receiver is bf16: halves bytes, buckets and round trips. Risk: fp32-only params (MoE gates, norms — the comment at `bucketed_weight_transfer.py:120-122`); needs an allow-list of names kept fp32, or ask vLLM for each param's dtype once (PR #8110 does the "verified receiver dtypes" idea for veomni only; #8327/#6045 are FP8 export; none covers plain FSDP bf16). Expected: **≈2× fewer IPC bytes, −30-50 % sync wall (est.)**.
- (b) **Double-buffer the bucket** (two IPC buffers, ack-after-load of k while filling k+1): overlaps all-gather+copy with `load_weights`. #5619 exists as a stale draft; a tight re-implementation on top of the current `BucketedWeightSender/Receiver` is small (≈150 lines). Expected: sync → max(gather, load) instead of sum, **−30-45 % (est.)**.
- (c) **Delta IPC for the hybrid path**: the backend already computes shard-local bf16 byte-diffs (`engine/utils.py hf_delta_export`, `prime_delta_snapshots`, used by `delta_sharded`, which is **disaggregated-only** per `delta_checkpoint_engine.py:14` and `docs/advance/delta_weight_sync.md`), and vLLM already has the in-place sparse apply (`verl_delta_ipc` WeightTransferEngine, `vllm_rollout/delta_weight_transfer.py`, `utils.py:184-189`). Measured changed ratio is 0.9-3 % of bf16 bytes/step (delta doc). Wiring the two together for colocated mode needs sleep level 1 (weights kept, offloaded to pinned host) instead of 2, so the engine still holds last step's weights to patch: +16 GB host pinned memory for 8B. Expected: 32.8 GB → ~0.5 GB on the wire; sync becomes wake(weights from host, ~0.6 s at 25 GB/s PCIe) + ~0.3 GB patch — **2-5× faster (est.)**, and no fp32 all-gather at all. Risk: medium (sleep-level semantics, LoRA/MTP exclusions at `vllm_async_server.py:1511-1527`).

### 3.2 `nccl` (`checkpoint_engine/nccl_checkpoint_engine.py`) — disaggregated

- Topology: actor rank 0 (+ its NVLink-local actor peers as relays when `multi_sender=True`, default `:142`, `:200-219`) broadcasts to every rollout `CheckpointEngineWorker` (`:221-250`). Ranks of other actor workers are −1 and only *walk the generator* because `full_tensor()` is collective (`:327-332`).
- Pipelined double buffer on the sender (`send_buf/recv_buf` swap, `:338-398`); metadata via ZMQ PUB/SUB (`:95-106`); receiver yields views of the landed bucket while the next broadcast is in flight (`:449-508`).
- Process group is built **every sync** unless `rebuild_group=False` and already initialised (`:297-305`; `CheckpointEngineManager.build_process_group` is called every `update_weights`, `base.py:536`); `finalize` destroys it only when `rebuild_group=True` (`:182-193`). Related open PRs: #6266/#6408 NCCL suspend/resume, #7045 fail-fast on hung init.
- Rollout side re-buckets the received tensors through the **same CUDA-IPC path** (`base.py:354-360` → `vllm_rollout.py:229-241`): one extra device copy per byte.
- Measured by the project (`delta_weight_sync.md`): Qwen2.5-7B 1+1 nodes 5.5-6 s; Qwen3-8B FSDP2 2+2 nodes 34 s; Qwen3-235B-A22B 246-266 s.

### 3.3 `nixl` (`checkpoint_engine/nixl_checkpoint_engine.py`) — disaggregated, RDMA

- A **linear chain** actor-rank-0 → rollout worker 1 → 2 → … → N (`build_topology`, `:288-305`): each worker RDMA-reads the previous hop's bucket and exposes it to the next (`:452-532`). Time ≈ (num_buckets + N − 1) × bucket_time; a 16 GB bf16 model in 2 GiB buckets with 8 rollout workers = 15 bucket-times. Metadata on a ZMQ side channel; two registered 2 GiB buffers per worker (`:273-286`).
- #8395 (open, 2026-10-26) proposes `sharded_nixl` with no trainer-side all-gather: each actor shard is read directly by the rollout workers.

### 3.4 `delta_sharded` (`checkpoint_engine/delta_checkpoint_engine.py`) — disaggregated, sparse

- Seed sync streams the full export values-only (`:470-567`); steady syncs ship only changed `(int32 position, value)` pairs gathered to rank 0 (`:569-665`, `delta_sync/sparse_gather.py:62-156`), broadcast with the NCCL group; receiver patches in place via SGLang custom loader or vLLM `verl_delta_ipc` (`:357-396`).
- Wire cost per changed element = 4 + 2 bytes → breaks even with dense bf16 at 33 % changed; measured 0.9-3 % → 10-30× fewer bytes. Project numbers: Qwen3-8B 2+2 nodes 3.3 s vs 34 s nccl.
- Limits: `hybrid_engine=False` only, bf16 only, vLLM path requires `data_parallel_size=1`, no quantized receiver (roadmap "delta shard for quantized (weight, scale)").

### 3.5 Backend comparison

| backend | default? | copies trainer→engine | overlap | per-step group setup | model-size scaling |
|---|---|---|---|---|---|
| naive (IPC) | **yes** | 3 (gather, bucket, load) | none (lock-step) | none | linear, fp32 bytes on FSDP |
| nccl | no | 4 (gather, send_buf, recv_buf, IPC bucket) + load | sender double-buffer | init_collective_group every sync unless cached | linear |
| nixl | no | 4 + load | per-hop pipeline | agent add/remove every sync | linear × (1 + N/buckets) |
| delta_sharded | no | sparse gather + broadcast + patch | streamed flushes | NCCL group (as nccl) | ~flat (≈1-3 % changed) |

## 2. Agent loop path (multi-turn, `rollout.multi_turn.enable=True` → `ToolAgentLoop`)

Per trajectory (`tool_agent_loop.py:131-213`, state machine PENDING→GENERATING→PROCESSING_TOOLS→TERMINATED):

| hop | code | cost per turn (est.) |
|---|---|---|
| tokenise initial prompt | `ct_build_initial_tokens` → `apply_chat_template` in the default thread-pool executor (`agent_loop.py:366-376`, `continuous_token.py:99-111`, `:226-241`) | 1-5 ms, GIL-bound Jinja |
| LLM call | `server_manager.generate(request_id=agent_data.request_id, prompt_ids=<whole conversation so far>)` (`tool_agent_loop.py:244-253`): **the full token prefix is re-sent every turn**; the *same* `request_id` keeps the sticky session (`router.py:180-185`) and the DP-engine pin (`vllm_async_server.py:845-850`), so vLLM's prefix cache serves the earlier turns *within* a step. | 2 Ray RPCs (acquire + generate) + request setup; prefill of only the new suffix on a cache hit |
| tool parse | `tool_parser.extract_tool_calls` (`:300-302`) | regex/JSON, <1 ms |
| tool exec | `_handle_processing_tools_state` → `asyncio.gather` of ≤ `max_parallel_calls` (default 1, rollout.yaml:214) `_call_tool` coroutines (`:316-321`); `BaseTool.create/execute/release` per call (`:486-496`) | tool-bound; a *synchronous* tool blocks the worker's event loop and every other trajectory on that worker |
| merge tool output | `ct_merge_context_msg` → `tokenize_context_incremental_messages` (`continuous_token.py:113-166`): renders a **synthetic 3-message prefix + the appended group twice** (prefix and full, `render_delta_token_id` `:243-260`, `_tokenize_tool_group` `:263-277`) and diffs → cost ∝ appended message + tool schema, **not** ∝ conversation length (only the DeepSeek-VL2 author does full re-render + diff, `:1527`). | 2-10 ms |

Reward: `_compute_score` runs per trajectory on a random `RewardLoopWorker` (`agent_loop.py:1052-1055`) — streamed, not on the trainer's critical path, but each call pads and ships the trajectory tensors through Ray.

Findings:
- A1 **Ray-hop overhead is per LLM call, not per token**: 2 RPCs + a Python `SamplingParams` build + `TokensPrompt` per turn (`vllm_async_server.py:683-703`), ~1-3 ms each (est.). With 4096 trajectories × ~10 turns = 40k calls/step → ~1-2 CPU-min across workers; small next to decode, but all `acquire_server` calls serialise on one actor (§1.2).
- A2 **Tool execution concurrency is per-trajectory `max_parallel_calls=1`** and there is no worker-level tool semaphore: 512 trajectories on one worker that all hit a sandbox at once will fan out 512 concurrent tool calls (the sandbox-fusion tool has its own rate limiter; function tools have none).
- A3 **Cross-step prefix reuse is impossible by construction**: wake resets the prefix cache (`vllm_async_server.py:932-933`), weight update resets it again (`vllm_rollout.py:247-248`), and `partial rollout` resume re-prefills the retained tokens (§1.4). For long agent prompts (system + tool schemas, typically 1-3k tokens shared by *every* trajectory) the system prefix is recomputed once per replica per step — cheap (one prefill) — but the per-trajectory retained prefix on resume is a full re-prefill: P0 on the roadmap.
- A4 `num_turns` and `__num_turns__` are tracked but the trainer never uses turn boundaries for scheduling; `max_assistant_turns` default `max_length // 3` (rollout.yaml:193-194).

## 4. Async modes

### 4.1 V1 `colocate_async` (`trainer_colocate_async.py`)
- Same GPUs for both; `num_warmup_batches=1` (yaml :250) pre-dispatches a batch before the first step so the buffer is non-empty.
- Step boundary: `on_sample_end` → `abort_replicas()` + `sleep_replicas()` (`:44-48`); `on_step_end` → `update_weights` (naive IPC, forced: `trainer_base.py:383` sets `backend = "naive"` for the hybrid replicas regardless of config) → `resume_generation_replicas()` (`:37-42`).
- **What is lost at the abort**: nothing in tokens (`FullyAsyncLLMServerClient` keeps `token_ids` and re-issues, `llm_server.py:294-366`), but every in-flight request pays: a 1 s client sleep (`:366`), a fresh `acquire_server` (new replica possible), and a **full re-prefill of prompt+retained tokens** because both caches were reset. For a trajectory aborted at 6k tokens that is 6k tokens of prefill at 7.5k-tok/s per replica (est. 8B bf16 TP2) ≈ 0.8 s of GPU per resumed trajectory; with ~1024 in flight at the switch, ≈ 100 s of aggregate replica time per step on re-prefill (est.) — this is the P0 roadmap item's entire payoff.
- Staleness: `ReplayBufferAsync` drops groups older than `max_off_policy_threshold=8` versions (`replay_buffer.py:520-529`) and refills exactly k (`:582-583`); `wait` strategy blocks instead (`:541-556`).

### 4.2 V1 `separate_async` (`trainer_separate_async.py`)
- Standalone replicas own generation (`:167-169`), served through `FullyAsyncLLMServerClient` (`:227-229`); the trainer runs `parameter_sync_step` (default 4, yaml :262) mini-batch updates per global step (`trainer_base.py:534-561`) and syncs to the standalone pool with the configured non-naive backend (`:69-70` asserts `backend != "naive"`; `:394-397`). Each `standalone_checkpoint_manager.update_weights` performs the full `abort → release_kv_cache → build_process_group → send/recv → finalize → resume_kv_cache → resume_generation` sequence (`checkpoint_engine/base.py:510-562`): generation on the standalone pool is **fully paused for the whole sync** (abort at `:523`, resume at `:560`), so every parameter_sync_step the rollout pool loses `T_sync` + the re-prefill of everything in flight.
- Decoupled PPO bookkeeping without bypass mode: `save_model_to_cpu/restore_model_from_cpu` per mini-batch (`:201-225`, N saves + 2(N−1) restores) — for an 8B fp32 master (32.8 GB) at ~20 GB/s PCIe that is ≈ 1.6 s per transfer, ≈ 16 s/step at N=4 (est.) unless `algorithm.rollout_correction.bypass_mode=True`.
- Hybrid switch (opt-in `enable_switch`, yaml :271): `switch_to_rollout` = naive `update_weights` on the hybrid replicas + `resume_generation` + `add_servers` to the standalone balancer (`:417-425`); `switch_to_trainer` = `remove_servers` + `abort_replicas(reject_request=True)` + `sleep` (`:427-434`). The adaptive threshold (`:304-338`) compares measured `benefit = remaining × per_sample_time × (1 − 1/scaling)` against a windowed switch cost (`:358-372`). The switch cost is dominated by the naive weight sync (§3.1) — so every improvement to §3.1 directly lowers the break-even for lending.
- Serialisation points that remain: (i) `update_weights` pauses the standalone pool; (ii) `replay_buffer.sample` polls at 2 s; (iii) `_compute_old_log_prob` CPU round-trips; (iv) `get_sampleable_count` does a full `kv_list` scan on every call (`replay_buffer.py:558-562`, called from `on_step_begin`, `on_sample_begin`, `on_step_end`).

### 4.3 Experimental recipes (V0-era): `one_step_off_policy`, `fully_async_policy`
- `one_step_off_policy` (`verl/experimental/one_step_off_policy/ray_trainer.py`): one batch of look-ahead, dedicated rollout GPUs, NCCL sync (doc `docs/advance/one_step_off.md`: step 749 s → 520 s on Qwen2.5-Math-7B; `wait_prev_gen` 45-59 s remains).
- `fully_async_policy` (`verl/experimental/fully_async_policy/`): Rollouter → MessageQueue → Trainer with `staleness_threshold`, `trigger_parameter_sync_step`, `partial_rollout` (doc `docs/advance/fully_async.md`: 2.35-2.67× at 128 H20 with staleness 0.5 + partial rollout; checkpoint-engine style sync 15.8 s → 4.4 s on 30B-A3B 16:16). Partial rollout there also resumes by re-prefill. The V1 `separate_async` is the supported successor (`docs/advance/v1_async_trainer.md`), and the roadmap marks V0 for removal; I treat these as reference numbers, not contribution targets.

## 5. KV cache and prefix sharing

### 5.1 GRPO siblings (n>1) — where the shared prompt prefix is computed

- The n samples of one prompt are n independent requests: V0 repeats the batch on the driver (`ray_trainer.py:1491`); V1 spawns n agent loops per prompt on one worker (`agent_loop_tq.py:127-134`). Each gets a fresh `request_id = uuid4().hex` (`single_turn_agent_loop.py:69`, `tool_agent_loop.py:127-128`).
- Routing: `GlobalRequestLoadBalancer.acquire_server` keys stickiness on `request_id` only (`router.py:170-204`); with no sticky hit it picks a random least-inflight replica (`:199-201`; tie-break randomised by merged #7613). So siblings land on **different replicas with probability ≈ 1 − 1/R per pair**. With R=4 replicas and n=8, the expected number of distinct replicas a group touches is `4·(1−(3/4)^8) ≈ 3.6`, i.e. the prompt prefill is computed **~3.6× per prompt instead of 1×** (est.). Within one replica vLLM's prefix cache (`enable_prefix_caching=True`, rollout.yaml:98) does share it, provided the siblings arrive close enough in time, which they do (all n are created back-to-back).
- Cost: with P=1.5k prompt tokens, B=512, n=8, the redundant prefill is `(3.6−1)·512·1.5k ≈ 2.0M tokens` per step out of ~6.1M prompt tokens + ~12-20M generated tokens → **≈8-12 % of the step's prefill work, ≈2-4 % of total rollout GPU time (est.)**. The KV-cache footprint matters more for long-prompt agent workloads: holding n copies of a 3k system+tool prefix across replicas instead of one shared block set per replica.
- DP engines: `session_id` pins a *multi-turn session* to one DP rank (`vllm_async_server.py:845-850`, merged #8179) — again keyed by `request_id`, so siblings also scatter across DP ranks.

**Smallest valuable step (roadmap "session-affinity routing for multi-turn agents" + #6122's "group sticky")**: make `acquire_server` accept an optional `group_id` (= prompt `uid`) and map the *first* sibling by least-inflight, later siblings to the same replica unless that replica's in-flight count exceeds the least-loaded by a slack (so a hot replica is not avalanche-loaded, cf. #7613/#7435). Plumbing: `require_acquire_fields` already allows per-router extra fields (`router.py:55-59`, `llm_server.py:69-80`), and `AgentLoopWorkerTQ._run_prompt` has `uid` in hand (`agent_loop_tq.py:114`). The identical change also pins the n siblings to one DP rank by passing `session_id=uid`. ~80 lines + a CPU test in `tests/workers/rollout/` (router is pure Python). Duplicates: #6122 (2026-04, EricWuji, targets `agent_loop/load_balance.py`, a file that no longer exists after merged #7115 made the router pluggable — bit-rotted, not merged), #6940 (draft KV-cache-aware router, external collectors, 40+ files), #6533/#7435 (sticky re-evaluation under imbalance, open). Nobody has claimed the roadmap line in #8186's thread.

### 5.2 Multi-turn: KV reuse across turns

Within a step: yes — same `request_id` → same replica and DP rank (`router.py:180-185`, `vllm_async_server.py:845-850`), content-hash prefix cache hits on the previous turns; the client re-sends the full token prefix every turn (`tool_agent_loop.py:244-253`) which is correct for vLLM's cache. `num_cached_tokens` is surfaced per request (`vllm_async_server.py:749`, merged #7565) so the hit rate is measurable without GPU access.

Across a weight switch: no — (i) `wake_up` → `reset_prefix_cache(reset_connector=True)` (`vllm_async_server.py:932-933`); (ii) `ServerAdapter.update_weights` → `clear_kv_cache` (`vllm_rollout.py:247-248`); (iii) `abort_all_requests(reset_prefix_cache=True)` on every non-naive sync (`checkpoint_engine/base.py:523`, `vllm_async_server.py:1198-1204`). Resumed partial rollouts re-prefill their whole retained prefix.

### 5.3 The prefix-sharing RFCs

- **#7561 / #6401 / #8299** are all **training-side** RFC issues, not rollout-side: #8299 (DeeproChoudhury, 2026-10-20, PR #8300) packs the n siblings as one trunk + n branches in the FSDP engine's varlen flash-attention call (reported 2.7× step speed-up on Qwen3-4B with a 2k shared prompt; 1.18× on GSM8K); #7561 (2026-08-26) proposes Tree Prefix Reuse in the Megatron engine with KV retained across branches and recomputed backward; #6401 (2026-05-19) proposes prefix-tree shared attention via MagiAttention on Megatron (multi-turn, arbitrary depth). None touches generation. Their rollout-side counterpart is §5.1: on the engine the shared prefix is already shareable through vLLM's prefix cache — the only missing piece is **co-locating the siblings** so that cache can hit. Smallest valuable step for the rollout: the group-affinity router of §5.1 (no kernel, no engine change, measurable with `num_cached_tokens`).
- **#8273** (cr-gao, 2026-10-18, open): `pause_generation(mode="keep", clear_cache=False)` keeps in-flight requests *and their KV* across a weight update, then resumes without re-prefill — the roadmap **P0 item, claimed by its author in #8186 on 2026-10-11**. Correctness caveat the PR must answer: KV computed under version k is reused to decode under version k+1 (a within-trajectory policy switch already accepted by partial rollout; the numerical mismatch is the same order as the one `rollout_correction` tracks). Do not duplicate; the complementary unclaimed piece is **salting instead of resetting** the prefix cache so that *finished* prefixes from version k are never hit under k+1 while in-flight ones are kept — which is exactly **#8323** (open, 2026-10-22, external KV caches salted by weight version). Together they make "no re-prefill on resume" safe.
- **#6990** (HanlinDu, open since 2026-07): Extra Prefix Cache via LMCache for the *static system/tool prefix* — warm once per weight version, read-only for all trajectories. That is the "centralized kv-cache pooling" roadmap line in practice; it needs an external LMCache server and new config surface (17 files). The in-engine alternative that needs no infra: issue one warm-up request per replica per step with the shared system prefix *before* the batch is dispatched, so the first wave does not compute it 256× concurrently (vLLM dedups only after the first prefill lands). ~30 lines in `AgentLoopManager.generate_sequences` / `prepare_step`; benefit limited to long shared prefixes.
- **#7277 / #7621** (FlexKV KV offload) — the "kv-cache offload" roadmap line; large (12-21 files), external dependency.
- **#8300** (open, 2026-10-20): shared-prefix *packing on the FSDP training side* (compute the prompt forward once for n siblings) — the training-side mirror of 5.1 and outside this slice, but it shows the group structure is already being exploited elsewhere.

### 5.4 Sleep/wake and the KV pool

`free_cache_engine=True` (default) → level-2 sleep discards weights **and** KV every step (`vllm_async_server.py:1511-1527`); wake re-maps both and the KV pool is re-profiled only at engine start (vLLM caches `num_gpu_blocks`), so the wake itself is cheap (`cuMemMap` of ~16 GB weights + ~40 GB KV ≈ 0.1-0.5 s, est.). The expensive part is the **full weight reload** that level 2 forces (§3.1). Level 1 (weights offloaded to pinned host, KV discarded) is only selected for LoRA/MTP/NPU — but it is the prerequisite for a colocated delta sync (§3.1 (c)). PRs #8032/#8046 touch the LoRA sleep interplay.

**C3 — Naive weight-sync fast path: bf16 at the sender + double-buffered IPC (F3, F4).** (a) In `EngineWorker.update_weights` naive branch, wrap `per_tensor_param` with a cast to the receiver dtype map (obtained once from the vLLM worker: `{name: param.dtype}` via `collective_rpc`), skipping names whose receiver dtype is fp32; (b) `BucketedWeightSender/Receiver` with two IPC buffers and ack-after-load. Benchmark: `timing_s/update_weights` on Qwen3-8B/8×H100 and Qwen3-32B; expect bytes 32.8→16.4 GB and ≈ −50-60 % wall combined; bit-exact greedy outputs before/after (reuse `test_correctness_on_gpu.py`). Supersedes stale #5619; #5378's naive correctness test is worth lifting.

**C4 — Colocated delta weight sync (F5).** New backend `delta_ipc` for hybrid replicas: seed step = today's naive path; afterwards level-1 sleep (weights to pinned host), `prime_delta_snapshots` after the seed, each step `hf_delta_export` on each rank's shard, batched sparse gather to rank 0 (`gather_slot_entries_to_rank0`) and broadcast over the **training** process group (no new NCCL group), then every rank feeds the flush stream to `ServerAdapter.update_weights(..., wire_format="delta_flush")` (`vllm_rollout.py:222-223`). Expected: ≈1-3 % of bf16 bytes on the wire, no `full_tensor()` all-gather, sync ≈ wake-restore (≈0.4 s for an 8 GB TP shard) + patch; 2-5× faster than C3's result. Benchmark: `update_weights` timer, `checkpoint_engine/changed_ratio`, greedy bit-exactness vs full sync after 50 steps (the delta doc's protocol). Risks: vLLM patch-API version, DP=1, no LoRA/quant; host pinned memory. Issue #6225 is the demand signal; nobody has claimed it.

**C5 — V1 control-plane dead time (F6).** Replace `time.sleep(2.0)` polling with a short poll (0.1 s) plus incremental `kv_list` (only `is_prompt` rows change status), and in `_validate` run the colocated-RM pass once after all validation batches instead of sleep→RM→full sync per batch (`trainer_base.py:1082-1085`, V0 `ray_trainer.py:643-650`). Benchmark: `timing_s/gen − t(last trajectory landed in TQ)` from the TQ tags (`seq_len`, `max_global_steps` timestamps) and `timing_s/testing`. Small, safe, immediately measurable without GPUs for the polling half.
