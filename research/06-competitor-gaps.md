## 1. Framework-by-framework notes

Evidence grade in brackets: [code] = read in source or a code-level doc, [doc] = project documentation, [readme/blog] = README or blog text, [paper] = arXiv paper.

### prime-rl (PrimeIntellect-ai/prime-rl)
- Known for: fully async orchestrator/trainer/inference split, FSDP2 trainer, vLLM inference, native `verifiers` environments (Environments Hub), 1T+ MoE on 1000+ GPUs target [readme]. README: https://github.com/PrimeIntellect-ai/prime-rl
- Async/staleness [doc, `docs/algorithms.md`]: inference at step n samples from policy max(0, n-1); bound `orchestrator.max_staleness` (default 8); tokens past the bound are *masked out of the loss* rather than the rollout being cancelled; a sample is dropped only when no trainable tokens remain. Staleness is split into in-flight (weight update mid-generation) and in-queue. Metrics `mismatch_kl_by_staleness/{bin}`.
- Mismatch corrections [doc]: default loss IPO masks tokens whose sampled-token *probability* change exceeds `eps` (0.3); `icepop` keeps tokens with trainer/inference ratio in `[ratio_low=0.2, ratio_high=5.0]`; `score_centering` with `score_centering_topk`. Per-component global-token normalisation.
- Trajectory merging [doc]: multi-step agent trajectories merge into one sample while the "extension property" (each prompt is an exact token prefix extension of the previous) holds; renderers enforce it via `bridge_to_next_turn`; on break, "graceful fallback to multiple samples". This is a clean answer to the "two kinds of multi-turn" problem.
- Filters [doc]: `AdvRangeGate`, zero-advantage drop, `constant_trainer_batch_size` refills filtered samples. Pre-generation prompt filtering is not described.
- Other [readme]: FP8 inference, PD disaggregation, EP/CP, LoRA, Slurm one-line deploy with `llm-d` router + Mooncake KV offload. No throughput numbers in README/docs read.

### slime (THUDM/slime)
- Known for: Megatron training + SGLang server-mode rollout with full argument pass-through; single `--colocate` flag; data buffer; custom rollout function; `/abort_request` for partial rollouts and DAPO-style dynamic sampling [blog https://lmsys.org/blog/2025-07-09-slime/]. README: https://github.com/THUDM/slime
- Weight sync [doc]: "Delta Weight Sync" over shared storage (`docs/en/advanced/delta-weight-sync.md`); external rollout engines with disk-based updates across GPU fleets; `--rollout-data-transport straw` (JuiceFS) [readme].
- Fully-async [readme]: `examples/fully_async` plus a GPU CI test; fault-tolerance and reproducibility guides exist (`docs/en/advanced/fault-tolerance.md`, `reproducibility.md`). No speedup numbers in README/blog.
- Multi-model server groups and PD disaggregation configs [readme].

### Miles (radixark/miles) — slime fork
- Known for [readme https://github.com/radixark/miles]: SGLang+Megatron (also FSDP2, torchtitan), decoupled rollout/training with configurable on/off-policy schedules, router with fleet health checks, in-loop weight updates "in seconds, even on a trillion-parameter model such as Kimi-K2.6", P2P RDMA fast path, MXFP8/NVFP4/FP8/INT4-QAT training, token-in-token-out, Rollout Routing Replay (MoE expert routing replay in trainer), engine failure recovery "without a restart", multi-LoRA into SGLang, connectors for Harbor/HUD/NeMo Gym/OpenEnv/Verifiers; tech report arXiv 2609.08368. README claims are qualitative (no numbers); "true on-policy / bitwise" is a blog claim I still need to verify (see Sources).

### AReaL (inclusionAI/AReaL)
- Known for: fully asynchronous RL with interruptible rollouts and decoupled PPO objective; boba² claims "2.77x speedup" vs synchronous [readme]; AReaL-lite "80% fewer lines of code"; AReaL 2.0 (2026-07) splits into training/inference/agent/weight-update microservices [readme https://github.com/inclusionAI/AReaL]. Paper arXiv 2505.24298; 2.0 report arXiv 2607.01120.
- Staleness [doc `docs/en/algorithms/async.md`]: `rollout.max_head_offpolicyness` (0 = sync, typical 2–8); `actor.use_decoupled_loss` requires `actor.recompute_logprobs=true`; "partial rollouts, where a single trajectory can be segmented across multiple policy versions"; sync mode "typically 2x slower".
- Algorithms [readme]: GRPO/GSPO/DAPO/LitePPO/Dr.GRPO/REINFORCE++/RLOO/SAPO/IcePop/KPop/M2PO; KPop = bidirectional binary-KL token masking. Backends: Megatron (DP/TP/SP/CP/PP/EP, packing, LoRA), FSDP2, "Archon" (FSDP2+PP+EP, no LoRA); SGLang default, vLLM. Weight update modes `disk`, `xccl`, AWEX.
- AReaL-DTA "Dynamic Tree Execution" (prefix-tree training) is cited by verl RFC #7561 as the inspiration; not verified from AReaL docs in this pass *(guess that it exists in AReaL code)*.

### NeMo-RL (NVIDIA-NeMo/RL)
- Known for [readme https://github.com/NVIDIA-NeMo/RL]: Automodel (PyTorch-native TP/SP/CP/EP/FSDP2) and Megatron backends; vLLM, Megatron-native inference ("no weight conversion"), SGLang (v0.6.0); async GRPO with replay buffers; sequence packing; FP8 E2E training and FP8 vLLM generation; speculative decoding "for rollout acceleration and training" (v0.6.0); NeMo-DCR "delta-compressed refit" for bitwise-exact sparse weight sync (preprint); NeMo Gym environments; x-token distillation across tokenizers (v0.7.0); Muon optimizer; chunked CE loss.
- Fault tolerance [doc `docs/design-docs/generation.md`]: opt-in SGLang `sglang_fault_tolerance_config` (health monitor + liveness probe, `rollout_max_restart_attempts`), router retries and circuit breaker; replacement engines wait for the next refit; streaming responses already started "cannot be replayed".
- Roadmap v0.7: resiliency (fault tolerance, auto-scaling). No README benchmark numbers; a discussion titled "Optimizing Weight Transfer in Large MoE Models by 10x".

### SkyRL (NovaSky-AI/SkyRL)
- Known for [readme https://github.com/NovaSky-AI/SkyRL]: skyrl-train, skyrl-gym (Gymnasium-API math/code/search/SQL envs), skyrl-agent (long-horizon agents), skyrl-tx (unified train+inference engine, Tinker API compatible), Harbor integration, Beam 501B-A23B day-0 with MXFP8 RL recipes.
- Fully async [doc https://docs.skyrl.ai/docs/tutorials/fully_async]: "pause the generation of the ongoing trajectories, 2) update the generator weights in-flight, 3) resume generation" implemented as *abort all in-flight `/chat/completions`, save partial results, re-feed on resume* (so a trajectory "can be generated by multiple model versions"); `trainer.fully_async.max_staleness_steps` (aggregate bound, 0 = sync); `generator.use_cache_salt` isolates prefix-cache blocks per policy version; `clear_kv_cache_on_weight_sync=false` reuses stale KV; no IS correction in current implementation ("Validate with correct algorithmic offset (importance weighting)" is future work); no speedup numbers.

### ROLL (alibaba/ROLL)
- Known for [readme https://github.com/alibaba/ROLL]: sample-level async parallel rollout, async reward, dynamic sampling, environment-level async rollout for agentic RL, TrajectoryWise (StarPO) and StepWise (GiGPO) paradigms, GEM-aligned env definition, vLLM dynamic FP8 rollout + remove_padding, FSDP2 and Megatron 5D, "extreme offload/reload", AutoDeviceMapping, LoRA on Megatron, GPU partial overlapping (2026-02).
- Papers: ROLL tech report arXiv 2506.06122; **ROLL Flash** (async) arXiv 2510.11345; **RollPacker** (tail batching for synchronous RL) arXiv 2509.21009; RollArt arXiv 2512.22560. Numbers to be confirmed from abstracts (see Sources).

### OpenRLHF
- Known for [readme https://github.com/OpenRLHF/OpenRLHF]: Ray + vLLM, hybrid engine (`--train.colocate_all` + sleep), async RLHF (`--train.async_enable`, `--train.async_queue_size`), **partial rollout via vLLM pause/resume** (`--train.partial_rollout_enable`, "in-flight samples may mix old and new weights"), NCCL/CUDA-IPC weight sync, DAPO dynamic filtering, packing, ring attention, LoRA/QLoRA, token-in-token-out `AgentExecutorBase`/`AgentInstanceBase` (reset/step), vLLM IS correction knobs (`is_correction_level` token|seq, `is_correction_mode` mask|clip, `is_correction_gating` ratio|binary_kl|tv), FlashREINFORCE (2026-09, "critic-free, single-rollout asynchronous RL"), Molt backend. No numeric speedups in README.

### RL2 (ChenmienTan/RL2)
- Known for [readme https://github.com/ChenmienTan/RL2]: "Ray Less" torchrun launch, ZeRO-3 default with DP/CP/TP (FSDP) and 5D Megatron, balanced sequence packing, SGLang async engine + SGLang Router, partial rollout, GEM gym-style envs, turns merged when `state + action` is a prefix of `next_state`, Dr. GRPO default. No numbers.

### TRL (huggingface/trl GRPOTrainer)
- Known for [doc https://huggingface.co/docs/trl/main/grpo_trainer]: vLLM colocate mode or server mode (`vllm serve --weight-transfer-config '{"backend":"nccl"}' --logprobs-mode processed_logprobs`), transformers continuous batching, `AsyncGRPOTrainer`, async reward functions, **vLLM importance-sampling correction on by default** (`vllm_importance_sampling_correction=True`, `vllm_importance_sampling_mode="sequence_mask"`, clip max 3.0; also `off_policy_mask_threshold`, `use_bias_correction_kl`), loss types dapo/dr_grpo/sapo/cispo/vespo, `scale_rewards` group|batch|False, `num_iterations`, `delta` two-sided clip, `beta=0` default (no reference model loaded), `cast_lm_head_to_fp32`, `top_entropy_quantile`, `tools=[...]` and `environment_factory` (stateful env per rollout, prefix-preserving chat template auto-patched for Qwen3/DeepSeek-V3), liger kernel. Single-process (accelerate) trainer: the canonical 1-GPU on-ramp.

### torchforge (meta-pytorch/forge)
- Status [readme https://github.com/meta-pytorch/forge]: "Development in Forge has paused"; LLM training moving to torchtitan. Was Monarch actor mesh + vLLM + torchtitan with async/sync switching and fault redirection claims. Treated as low-signal for gap analysis.

### RLinf
- Known for [readme https://github.com/RLinf/RLinf]: embodied/agentic RL, hybrid execution "up to 2.434x throughput" for embodied RL, DynaRL (OSDI 2026) dynamic reallocation across heterogeneous RL components, FSDP+HF/SGLang/vLLM and Megatron backends, many accelerators. Paper arXiv 2509.15965. Mostly orthogonal (robotics) to verl's core.

### rllm (rllm-org/rllm)
- Known for [readme https://github.com/rllm-org/rllm]: agents as plain functions (`@rllm.rollout`), Episode/Trajectory/Step hierarchy, `@rllm.evaluator`, **gateway that "transparently captures token IDs and logprobs"** via `config.base_url` (the `rllm-model-gateway` package referenced in verl RFC #5790), sandboxes (Docker/Daytona/Modal) with snapshot/warm pools, backends verl / tinker / fireworks, "Fully Async Training" recipe (2026-02), 60+ benchmarks via Harbor. No numbers.

### oat (sail-sg/oat)
- Actor-Learner-Oracle with vLLM actors, DeepSpeed learners, Mosec oracle; Dr. GRPO origin; small-scale research framework [readme https://github.com/sail-sg/oat]. Low relevance to verl gaps.

### PipelineRL (ServiceNow)
- Known for [readme https://github.com/ServiceNow/PipelineRL, paper arXiv 2509.19128]: actor/preprocessor/trainer split over streams (filesystem or Redis); "After each optimizer step, updated weights are broadcast to the inference servers without halting sampling" (the vLLM worker's `receive_weight_update` pauses inference, NCCL-broadcasts, reloads); `cfg.finetune.max_lag` / `weight_update_interval`; simplified GRPO (no value net, no clipping, no KL by default). Results claim parity with Open-Reasoner-Zero on AIME-24/MATH-500 for 7B/32B. Throughput numbers to be taken from the paper (see Sources).

### Tinker (Thinking Machines; hosted API) — API ideas only
- Primitives [doc https://tinker-docs.thinkingmachines.ai/]: `TrainingClient.forward_backward`, `optim_step`, `save_weights_for_sampler`, `SamplingClient.sample`, futures (`APIFuture`), LoRA-only training "from 1B to 1T+"; cookbook abstractions `Env`, `EnvGroupBuilder`, `RLDataset`, `Trajectory`, `TrajectoryGroup`, `compute_advantages`, `assemble_training_data`, renderers (`Renderer`, `TrainOnWhat`), loss functions incl. importance sampling / PPO / CISPO / DRO / GSPO, "Clock Cycles & Pipelining" and "Async Patterns" guides. verl already ships `verl/workers/engine_workers_tinker.py` (Tinker-style `optimizer_step` param-group overrides), so the API idea is partially absorbed.

### Unsloth RL
- Known for [docs https://docs.unsloth.ai/new/memory-efficient-rl, https://unsloth.ai/docs/new/grpo-long-context]: single-GPU LoRA/QLoRA GRPO with vLLM weight sharing and "Standby" (sleep) feature; claims "10x longer context ... 90% less VRAM" vs other GRPO LoRA implementations and ~7x longer context batching (Feb 2026); e.g. Qwen3-8B GRPO at 110K context on one H100. Vendor numbers. Represents the 1-GPU "unified trainer" use case verl does not target.

### Papers / research systems (no verl-comparable code unless noted)
- **RhymeRL** (arXiv 2508.18588, SJTU+ByteDance): HistoSpec = speculative decoding drafting from the *previous epoch's rollouts of the same prompt* (suffix-tree style); HistoPipe = history-length-aware two-tier scheduler; authors claim 2.6x. [paper]
- **SpecActor / "Fast LLM Post-training via Decoupled and Fastest-of-N Speculation"** (arXiv 2511.16193, SJTU+ByteDance Seed): decoupled drafter/verifier on separate GPUs for large per-worker batches, Fastest-of-N draft selection; claims 2.0–2.4x rollout, 1.4–2.3x E2E. verl has a WIP draft PR implementing it: #5757 (`verl/experimental/decoupled_spec/`). [paper + OPEN PR]
- **SPEC-RL** (mentioned in search results): reuses prior trajectory segments as speculative prefixes with draft-and-verify. [paper, not read]
- **Laminar** (arXiv 2510.12633, HKU+ByteDance Seed): trajectory-level asynchrony via relay workers (distributed parameter service) and dynamic repack of long-tail trajectories; up to 1024 GPUs; a secondary source quotes "up to 5.48x" (unverified against the PDF). [paper]
- **TreePO** (arXiv 2508.17445): tree-structured rollout sharing prefixes, branching at uncertainty, pruning and refilling; authors claim same accuracy at up to 43% fewer GPU hours. **Tree-GRPO** (arXiv 2509.21240, ICLR 2026): agent-step tree nodes, shared prefixes increase rollouts per token budget. "TreeRL" was not found. [paper]
- **StreamRL** (arXiv 2504.15930), **RollPacker** (arXiv 2509.21009), **ROLL Flash** (arXiv 2510.11345), **AsyncFlow** (arXiv 2507.01663), **Magistral** (arXiv 2506.10910): all cited by verl's own `docs/advance/fully_async.md` as the lineage of `fully_async_policy`.
- **Marin**: no RL framework surfaced in search; treated as not applicable.

## 2. Technique matrix

Format per row: **technique** — who has it (evidence grade, claimed gain) — **verl: STATUS** with evidence. verl paths are relative to the clone root; the default trainer is V1 (`verl/trainer/ppo/v1/`, `trainer.use_v1: true`), with `verl/workers/engine_workers.py` + `verl/workers/engine/` as the actor/critic/ref engine layer. The 26Q4 roadmap (#8186) marks `verl/trainer/ppo/ray_trainer.py` (V0) and `verl/experimental/{fully_async_policy,one_step_off_policy}` for removal/relocation to verl-recipe, so anything that only lives there is counted as "HAS (legacy path)".

### 2.1 Pipeline / scheduling techniques

1. **Fully asynchronous rollout–train pipeline with a staleness bound** — AReaL (`rollout.max_head_offpolicyness`, 2.77x claim [readme/paper]); prime-rl (`orchestrator.max_staleness`, token-level staleness masking [doc]); SkyRL (`trainer.fully_async.max_staleness_steps` [doc]); ROLL Flash (2.24x RLVR / 2.72x agentic [paper abs]); Laminar (trajectory-level, relay workers, up to 1024 GPUs [paper]); PipelineRL (~2x on 128 H100 [paper abs]); OpenRLHF (`--train.async_enable` [readme]); NeMo-RL (async GRPO + replay buffers [readme]); Tinker (`AsyncConfig.max_steps_off_policy`, off-by-K, no in-flight changes [doc]). **verl: HAS** — V1 `separate_async` / `colocate_async` (`verl/trainer/ppo/v1/trainer_separate_async.py`, `trainer_colocate_async.py`, `replay_buffer.py::ReplayBufferAsync._stale_terminal_keys`, `docs/advance/v1_async_trainer.md`); legacy `verl/experimental/fully_async_policy` (`async_training.staleness_threshold`, 2.35–2.67x on 128 GPUs per `docs/advance/fully_async.md`); dynamic hybrid scheduling (`docs/advance/dynamic_schedule.md`, +15.3%). Residual gap: per-staleness-bin mismatch metrics (prime-rl `mismatch_kl_by_staleness`) — small, MISSING.

2. **In-flight weight updates without draining (keep KV, no re-prefill)** — PipelineRL ("broadcast ... without halting sampling" via worker pause + NCCL [readme/paper]); OpenRLHF (`--train.partial_rollout_enable`, vLLM pause/resume [readme]); SkyRL (abort in-flight `/chat/completions`, save partial results, re-feed [doc]); Miles ("in-loop in seconds, even on ... Kimi-K2.6" [readme]). **verl: HAS abort+resume with re-prefill; KV-preserving variant is an OPEN PR** — V1 partial-rollout client retains tokens/logprobs, retries through the load balancer, "KV cache is reconstructed for the retained prefix" (`docs/advance/v1_async_trainer.md`); PR #8273 (cr-gao, 2026-10-18, non-draft) adds vLLM `pause_generation(mode="keep", clear_cache=False)` to keep KV/tokens/logprobs/MoE routing; this is roadmap #8186 "P0 Token-level interrupt + persist KV cache / routing across weight switch". Ownership: high.

3. **Partial rollouts / straggler abort-and-resume / tail batching** — slime (`/abort_request` reclaiming partial content [blog]); AReaL (trajectory segmented across policy versions [doc]); RL2 (partial rollout [readme]); RollPacker (tail batching: long-tail prompts deferred into "long rounds"; 2.03–2.56x vs verl sync, up to 128 H800 [paper abs]); StreamRL (output-length ranker + skewness-aware dispatch, up to 2.66x [paper abs]); RhymeRL HistoPipe (history-length-aware two-tier scheduler [paper]). **verl: HAS partial rollout; MISSING length-aware tail scheduling for the sync/colocate path** — partial rollout in V1 (`FullyAsyncLLMServerClient`, `docs/advance/v1_async_trainer.md`), metrics PR #8117; no `tail batching`/`length predictor`/`long round` code found (`grep -rn -iE 'tail.?batch|long.?round|length.?predict|ranker' verl` = 0 hits); roadmap item "P1 Sample-level dispatch: dispatch next prompt once #completed samples >= group size" is adjacent but different. Old ask: issue #658 (17 comments, adaptive per-prompt token budgets prototyped by a commenter).

4. **Speculative decoding inside RL rollouts** — NeMo-RL (v0.6.0 "Speculative Decoding support for rollout acceleration and training" [readme]); RhymeRL HistoSpec (drafts from last epoch's rollouts of the same prompt, 2.6x claim [paper]); DAS (suffix-tree drafter from recent rollouts + length-aware budgets, "up to 50%" rollout time [paper abs]); SpecActor (decoupled drafter/verifier, 2.0–2.4x rollout [paper]); Miles/slime via SGLang MTP (not verified in docs). **verl: HAS model-native MTP; everything else is OPEN PRs** — MTP rollout for vLLM/SGLang with drafter weight sync (`verl/workers/rollout/vllm_rollout/utils.py::build_mtp_speculative_config`, `_use_mtp_drafter_weight_sync`; `docs/advance/mtp.md`); EAGLE/EAGLE3 PR #5925 (open since 2026-04-08, updated 2026-09-21, non-draft, 14 files); vLLM suffix decoding PR #6342 (2026-05-14); DAS implementation PR #8396 (draft, 2026-10-26, 38 files, `docs/advance/das.md`); decoupled speculation (SpecActor) PR #5757 (WIP draft, `verl/experimental/decoupled_spec/`); RFC #4791 (suffix+LSTM). Ownership: high (four PRs).

5. **Prefix/KV sharing across GRPO samples and multi-turn — rollout side** — all vLLM/SGLang-based frameworks get engine prefix caching; SkyRL salts prefix cache per policy version (`generator.use_cache_salt`) and can keep stale KV (`clear_kv_cache_on_weight_sync=false`) [doc]; prime-rl Slurm recipe uses `llm-d` router + Mooncake KV offload [readme]; NeMo-RL Megatron inference has prefix caching with LRU/TTL/routing alpha [doc]. **verl: HAS** — `enable_prefix_caching: true` default (`verl/trainer/config/_generated_ppo_trainer.yaml`), Mooncake KV offload (`docs/perf/rollout_kv_offload.md`, hard reset at every weight update), session pinning to a vLLM DP rank (merged #8179). OPEN PRs: #8323 "salt external KV caches by weight version instead of resetting them" (the SkyRL idea), #6990 Extra Prefix Cache warm-up for agentic system prefixes.

6. **Prefix sharing — training side (compute the shared prompt once; prefix-tree attention)** — AReaL-DTA (depth-first prefix-tree forward/backward, one root-to-leaf path in memory, load-balanced multi-GPU tree batching; up to 8.31x over dense and 1.70x over sparse training on tau2-bench, 30–40% less peak memory; code on AReaL `feat/dta` branch [paper arXiv 2602.00482, ICML 2026]); MiniMax Forge "Prefix Tree Merging" (cited by RFC #6401). **verl: HAS a narrow form (PrefixGrouper); general packing is OPEN PRs** — `use_prefix_grouper` monkey-patched attention (`verl/models/transformers/monkey_patch.py::_create_prefix_grouper_wrapper`, used by fully_async/one_step_off trainers); PR #8300 "shared-prefix packing for the FSDP engine" (DeeproChoudhury, 2026-10-20, non-draft, 29 files; claims 2.7x step on Qwen3-4B with 2k shared prompt, 1.18x on GSM8K, 3.8x fwd+bwd at 8k prompt; RFC #8299); PR #6689 prefix-tree MAGI attention for Megatron (RFC #6401, 8 reactions); RFC #7561 Tree Prefix Reuse for Megatron (AReaL-DTA style). Multi-level trees on FSDP (depth-first AReaL-DTA execution) remain unclaimed. Ownership: high for one-level packing; medium for multi-level FSDP.

7. **Tree-structured rollouts (segment-wise branching with shared KV; depth-wise advantages)** — TreePO (arXiv 2508.17445: branch at uncertainty, prune, refill; "up to 43% fewer GPU hours" at same accuracy [paper/ICML slides]); Tree-GRPO (arXiv 2509.21240, ICLR 2026: agent-step tree nodes, more rollouts per token/tool budget [paper]). No surveyed framework ships it as a first-class feature (ROLL lists GiGPO step-wise, not tree sampling). **verl: MISSING** — no `tree`/`TreePO` rollout code or PR (`grep` of clone and `prs_open.json` = 0); only RFC #7561 mentions Tree-GRPO as a *training-side* motivation. Nothing on the roadmap. Ownership: low.

8. **Dynamic sampling and prompt filtering before generation (curriculum by difficulty / pass-rate history)** — prime-rl post-gen filters (`AdvRangeGate`, `constant_trainer_batch_size` refill [doc]); OpenRLHF `--algo.dynamic_filtering_*` [readme]; ROLL "dynamic sampling" [readme]; TRL `scale_rewards`/filters; none document a pre-generation difficulty scheduler. **verl: HAS post-generation DAPO filtering; pre-generation curriculum only as stale PRs** — `ReplayBuffer._dapo_filtered_keys` (`verl/trainer/ppo/v1/replay_buffer.py`), `filter_groups` metrics (`verl/utils/tracking.py`); hook comment "user can dynamically adjust n for each sample here, e.g according to task difficulty" (`verl/trainer/ppo/v1/agent_loop_tq.py:118`); AdaRFT PRs #1020/#1021 (open since 2025-04-11, targets V0 `ray_trainer.py`), CoDaPO PR #7497. Competitor evidence is weak, so this is a verl-internal opportunity more than a competitor gap.

### 2.2 Correctness / numerics techniques

## 3. Ranked top-10 gaps

Ranking weighs (a) value to verl users (speed or a needed capability, with demand signals from the issue dump), (b) implementation size and whether one PR can carry it, (c) whether a benchmark can prove it, and (d) the risk that a maintainer, sub-project or open PR already owns it. Items that are high-value but clearly owned are kept in the list (they matter for the overall picture) but marked "do not take". Summary of the matrix: of ~30 techniques, verl HAS 18 outright, 7 are OPEN PRs/RFCs, and 5 are MISSING with no owner.

### 1. Tree-structured rollouts with shared-KV branching (TreePO / Tree-GRPO) — verl: MISSING, unowned
- Competitor evidence: TreePO (arXiv 2508.17445; authors claim same accuracy at up to 43% fewer GPU-hours), Tree-GRPO (arXiv 2509.21240, ICLR 2026; more rollouts per token/tool budget by sharing agent-step prefixes). No surveyed framework ships it as a feature, so this would also be a first for open-source frameworks.
- Demand in verl: indirect — RFC #7561 (Tree Prefix Reuse) and RFC #6401 (8 reactions) cite Tree-GRPO/BPO/rStar-Math as the workloads that create shared prefixes; nothing asks for the sampler itself.
- Size: M (sampler) to M–L (with advantage estimator and metrics). One PR is feasible if scoped to "tree sampling agent loop + depth-wise GRPO advantage + config".
- Files: new `verl/experimental/agent_loop/tree_agent_loop.py` (segment-wise generation through the OpenAI-compatible replica server with `max_tokens` per segment, fan-out `branch_factor` at segment boundaries, prune/refill under a leaf budget; relies on engine prefix caching, which is on by default); `verl/trainer/ppo/core_algos.py` (`@register_adv_est` depth-wise sub-group advantage as in TreePO §3); `verl/trainer/ppo/v1/agent_loop_tq.py` (group bookkeeping: one prompt → variable number of leaves, same hook as the "dynamically adjust n" note at line 118); config in `verl/trainer/config/` (agent section) and `docs/advance/agent_loop.rst`. PR #7580 (`loss_weight` per output row) is the natural way to weight leaves; PR #8300 would later dedupe the shared prefixes in training.
- Benchmark: fixed leaf count per prompt, compare generated tokens/s, prefix-cache hit rate (vLLM metrics already scraped by `prometheus_utils.py`) and GPU-hours to a target GSM8K/MATH score vs plain GRPO with `rollout.n` = leaves; Qwen2.5-1.5B/3B on 1–2 GPUs is enough to show the throughput side.
- Ownership risk: low. Risk that maintainers route algorithmic recipes to verl-recipe: medium (keep the sampler generic and the advantage estimator a registered plugin).

### 2. Multi-level shared-prefix (tree) training on the FSDP engine, AReaL-DTA class — verl: OPEN PR for one level, multi-level unowned on FSDP
- Competitor evidence: AReaL-DTA (arXiv 2602.00482, ICML 2026; code on AReaL `feat/dta`): depth-first prefix-tree forward/backward, "up to 8.31x over dense training and up to 1.70x over sparse training" on tau2-bench, 30–40% lower peak memory. MiniMax Forge prefix-tree merging (cited by RFC #6401).
- verl status: PR #8300 (non-draft, active 2026-10-22) packs the `rollout.n` samples of one prompt as trunk + branches on FSDP (claims 2.7x step on a 2k shared prompt); PR #6689 does arbitrary-depth trees on Megatron via MAGI attention; RFC #7561 proposes TPR on Megatron. Multi-turn, multi-level trees on FSDP (where most agentic users are) remain unclaimed; RFC #8299 only sketches "a path to hybrid linear-attention models".
- Demand: #6401 (8 reactions, 4 comments incl. a third-party lab that already runs MAGI prefix merging), #7561 (2), #8299 (1); agentic multi-turn users dominate the recent issue stream (#8250, #6583).
- Size: L. Files: `verl/workers/engine/fsdp/transformer_impl.py` (micro-batch forward with branch-aware `cu_seqlens`/position ids), `verl/workers/utils/padding.py`, `verl/utils/seqlen_balancing.py` (pack by tree, not by sample), `verl/workers/utils/losses.py` (per-leaf token accounting), `verl/models/transformers/monkey_patch.py` (attention wrapper, as PrefixGrouper does today), tests under `tests/models/`.
- Benchmark: actor+ref forward/backward time and peak memory vs rmpad on multi-turn tool trajectories with 50–80% shared tokens; bitwise log-prob equality against the rmpad path (PR #8300 already has this harness).
- Ownership risk: medium–high (coordinate with DeeproChoudhury's #8300 and arvyanh's #6689; building on #8300's branch layout is the sane path).

### 3. Length-aware dispatch and token-budget routing for rollout (StreamRL / RollPacker / RhymeRL-HistoPipe) — verl: MISSING, unowned
- Competitor evidence: StreamRL output-length ranker + skewness-aware dispatch (up to 2.66x, arXiv 2504.15930); RollPacker tail batching (2.03–2.56x vs verl *sync* on up to 128 H800, arXiv 2509.21009); RhymeRL HistoPipe (history-length-stable scheduling, part of a 2.6x claim). All exploit that per-prompt response length is stable across epochs.
- verl status: dispatch order is dataset order; `GlobalRequestLoadBalancer` is least-in-flight-count (`verl/workers/rollout/router.py:171`); no length predictor anywhere (grep = 0). The async paths hide the tail; the default V1 `sync` mode and `colocate_async` still pay it. Old ask #658 (17 comments) prototyped per-prompt token budgets.
- Size: S–M, self-contained: (i) a per-prompt response-length EMA store keyed by prompt uid/hash (a small Ray actor or TransferQueue metadata) updated from `agent_loop_tq.py` results; (ii) longest-predicted-first submission order in the agent-loop manager (`verl/experimental/agent_loop/agent_loop.py` generate path / `verl/trainer/ppo/v1/agent_loop_tq.py`); (iii) optional router scorer "least outstanding tokens" (prompt + remaining budget) as an opt-in `RequestLoadBalancer` implementation next to `GlobalRequestLoadBalancer`.
- Benchmark: rollout-stage wall time, replica idle fraction and step-time variance over a 2-epoch GSM8K/DAPO-17k run (epoch 2 has history) on 2–8 GPUs; expect gains to scale with length skew.
- Ownership risk: low for (i)/(ii); medium for (iii) because `router.py` is contested by #6940 (draft KV-aware balancer), #6533 (draft imbalance gate) and the roadmap's "session-affinity routing" item — keep (iii) as a separate, tiny opt-in class.
